  1. 90 of 100 apps are buildable as a toolkit today; 72 already combine self-serve creds with an official MCP.
  2. OAuth2 dominates overall (78/100) and is universal in CRM (10/10) and productivity (10/10). Scraping/SEO is the API-key pocket (5/10 apps).
  3. 89/100 apps are self-serve. Gating clusters in ads (Google Ads, Meta Ads, LinkedIn Ads, Threads (Meta)) and finance (Plaid, PitchBook), not in support, comms, or developer platforms.
  4. Official MCP already exists on 80/100 apps, including all 10 developer/infra tools. The MCP-missing cluster is consumer messaging (Discord, Telegram, WhatsApp Business), plus a few email APIs -- not meeting-note apps.
  5. Top blockers are admin/app-review (7: Google Ads, Meta Ads, LinkedIn Ads, Threads, Amazon SP, DealCloud, Plaid), then paid data (SE Ranking, PitchBook), partnership (Salesforce Commerce Cloud), and no public API (Sherlock, NotebookLM).
  6. Easy toolkit wins: ship CRM, support, and infra first (10/10 infra already official MCP). Outreach-needed is 12 apps. 10 more have a usable REST API today but no vendor MCP (Discord, Telegram, WhatsApp, Mailchimp, SendGrid).

How to read this

An agent searched public docs with Composio (COMPOSIO_SEARCH_WEB, COMPOSIO_SEARCH_FETCH_URL_CONTENT), then filled one JSON row per app. A human scored a stratified sample of 20 (two per category) against vendor pages, then re-ran extract-only on misses. Treat toolkit_today as “a developer can get creds and call an API or official MCP without a partnership wait.” possible_with_work means an API exists but review or a paid plan sits in front. blocked means no usable public API for this product. Paid logins were skipped on purpose.

Agent

Composio ran a web search per app, fetched the top vendor/doc URLs, packed snippets, and a Groq model (Qwen 3.8 27B / gpt-oss-20b, sharded to stay under free-tier caps) returned one schema row. Cache lives in cache/<id>/ so research is not repeated. A second pass was extract-only on failed sample rows after prompt rules for vendor-domain MCP, paid vs self-serve, and sibling-product APIs.

Where a human was required

  • JS-only or login-walled docs still need a human click
  • MCP official vs community is easy to mix up when blogs copy vendor docs
  • paid vs self_serve (credits/plans) and sibling-product APIs (Mailchimp GraphQL) still miss
  • Rows the agent marked needs_human: NotebookLM.

Limits — said plainly

The agent can still confuse sibling products (Mailchimp Marketing REST vs Open Commerce GraphQL) and over-call MCP (Gumroad). It labeled Ahrefs self-serve/broad instead of paid/medium. Breadth (Otter) is judgment, not a hard fact.

Blocked (3)

  • Salesforce Commerce Cloud: Requires Salesforce partnership or enterprise contract to obtain instance credentials and API access; not self-serve for general developers.
  • Sherlock: No public API; CLI-only tool
  • NotebookLM: No official public API; only community‑built MCP that relies on browser cookies

Outreach / possible with work (7)

  • Google Ads: requires developer token approval
  • Meta Ads: Requires app review and approval for production access tokens
  • LinkedIn Ads: Requires LinkedIn Marketing API Program approval and OAuth 2.0 setup
  • Threads (Meta): Requires Meta app review and approval for Threads API access
  • Amazon Selling Partner: Developer registration and approval required
  • Plaid: Production API access requires approval/admin review after signup
  • PitchBook: Requires standalone contract and specific API credits; not self-serve.

JS-only or login-walled docs were not opened as a user. Confidence is the model’s, not a measured probability. MCP “official” means vendor-domain docs in the fetch pack, which can lag a product launch by days.
